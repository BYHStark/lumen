# ADR 0001：为什么做 Lumen，以及主线技术选择

- 状态：已接受
- 日期：2026-10-15

## 背景

这个仓库是长期学徒项目。目标不是堆一个能跑的演示，而是在一个产品里碰到合格 Go 后端会遇到的失败、并发和数据正确性问题。聊天上下文不够长，所以决定、课程和进度都放在仓库里。

## 决定

产品是多租户 API 计量、账本和 Webhook 可靠投递。三个进程：`lumen-api`、`lumen-worker`、`lumen-scheduler`，外加运维命令 `lumen`。

主线选择：

- Go 目标版本 1.27。本机初始化时是 1.24.13，所以 `go.mod` 先写 1.24.0，升级后再改。
- PostgreSQL + pgx，SQL 先手写。
- Redis 只做限流、锁和缓存。
- HTTP 用标准库和 chi。
- 金额用 `int64` 最小货币单位。
- 投递保证 at-least-once，不保证 exactly-once。
- 日志用 `log/slog`。

## 放弃的选项

- 博客、聊天室或商城：失败不够密集，或者容易陷进前端。
- Gin、Kratos、go-zero 或 ORM 当骨架：机制没学会时，框架换不走。
- 一开始拆很多微服务或上 Kubernetes：边界成本盖过语言和正确性训练。
- `float64` 金额：无法安全表示货币。

## 后果

阶段 9 之前不引入 sqlc、OpenAPI 生成、gRPC 或外部消息队列。要推翻某条决定，新写一篇 ADR，不在代码里悄悄换。
